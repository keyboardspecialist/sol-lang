# Sol Inspection Schema

`sol inspect <file.sol|package-directory>` emits exactly one compact JSON object on successful compilation. The current outer `sol.inspection` version-2 envelope contains producer and package metadata plus six always-present, independently tagged artifacts: version-2 `syntax` and `types`, and version-1 `hir`, `effects`, `contracts`, and `diagnostics`. `sol-inspection-2.schema.json` is the current self-contained structural contract; `sol-inspection-1.schema.json` remains the unchanged historical version-1 contract. `tests/inspection_cli/validate_inspection.py` checks current cross-record invariants without third-party packages.

Consumers must ignore unknown object fields. The tagged `kind` enums defined by version 1 are closed: consumers must not accept an unknown value as a version-1 kind. New records using known kinds and new optional fields are additive changes. Introducing a new tagged kind requires a new version of each affected artifact unless that artifact explicitly declares the field to be an open extension point. Removing or changing the meaning or type of a required field, changing ID interpretation, or changing ordering semantics requires a new outer or affected artifact version. Artifact versions may advance independently only when the outer schema explicitly permits that combination.

Paths are normalized `/`-separated package-relative paths and never identify the invocation's absolute root. Spans use zero-based half-open byte offsets in the named original file. Source `byteLength` is the exact byte count; `sourceBase64` is standard padded base64 of the original bytes and is the lossless source representation. Other JSON strings are valid UTF-8; invalid source bytes in textual projections are escaped as deterministic `\u00XX` markers and are not a byte round-trip mechanism. File, declaration, expression, table, occurrence, row, obligation, and snapshot arrays retain deterministic compiler insertion/source order unless a field explicitly describes set normalization. Diagnostic items preserve diagnostic insertion order.

Top-level declarations and references use `sem:1:<32 lowercase hex>` semantic IDs. Dense non-top-level identifiers such as `expr:0`, `local:0`, `type-parameter:0`, `type-app:0`, and bounded integer member/parameter indexes are snapshot-local and have meaning only inside one inspection object. They must not be persisted as cross-build identities. `arenaCounts` are counts, not serialized arena layouts. `provenanceMappings`, `patternVariantResolutions`, and `argumentFieldResolutions` are intentionally dense nullable mappings whose array index is the snapshot-local subject ID; other resolution/fact arrays carry an explicit subject.

Syntax version 2 adds the closed `tuple` expression kind and a `base` expression reference on field expressions. Types version 2 adds the closed `tuple` application constructor; tuple applications have 2 through 16 ordered type arguments and no semantic definition. `tupleProjections` is an expression-indexed dense nullable mapping: a non-null value is the exact zero-based ordinal selected by that field expression and is bounded by the base expression's tuple application arity. The compiler validates that relationship before rendering; the schema bounds all ordinals to the language limit of 0 through 15, and the reference validator resolves the field base and its type application to check the exact bound.

This schema is a selected stable semantic projection. It intentionally excludes C ABI or struct-layout compatibility, pointer values, allocation capacities, native sentinel values, C enumeration numbers, compiler-internal or machine IR, a deserialization API, cache-key suitability, and a guarantee that every compiler-internal fact is exposed. Compilation failures retain the established ordered `sol.diagnostic/1` JSON array; load and infrastructure failures retain `sol.cli-error/1`. Construction failures emit no partial successful inspection envelope. Output transport can truncate an already constructed envelope and returns status 1; allocation failure and usage return 1 and 2 respectively.
