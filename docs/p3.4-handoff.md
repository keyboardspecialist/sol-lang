# P3.4 Implementation Handoff (Historical Design Snapshot)

This is the approved pre-implementation P3.4 design, captured against baseline
commit `1c30291` (`define runtime cleanup and failure policy`). It is not a
progress report or a second queue: `TODO.md` remains the live and sole authority
for status and execution order. At capture, P3.1--P3.3 were complete for the
frozen E6 profile and P3.4 was the next production checkpoint.

## Objective and Boundary

Add a separate, bounded, backend-independent `SolMirRuntimeHostAbi` owner. It
borrows authenticated immutable `SolMirRuntimeConventions` (P3.1),
`SolMirRuntimeValues` (P3.2), and `SolMirRuntimeCleanup` (P3.3), all of which
must outlive it. It closes the *descriptive* capability and trusted-host ABI
policy over the complete P2 graph:

- preserve each capability root's identity and derived/private-source lineage;
- assign canonical host-operation and host-import descriptors to the exact P3.1
  host requirements and imports;
- express E3-safe, data-only arguments and the already-closed P3.2f result
  transfer vocabulary;
- state entry-specific root bindings, grants, and pure authority/import
  preflight; and
- provide finite test-only models of host invocation, result transfer, and
  bounded host failure detail.

It reuses rather than duplicates P2 recipes/layouts/operation provenance, P3.1
signatures, imports, identities, symbols, sites, failure codes, and E2 exits;
P3.2 allocation, ownership, and host-result plans; and P3.3 cleanup and
failure-precedence policy. It must not renumber, broaden, or reinterpret any
predecessor record.

P3.4 does **not** add an interpreter change, production host adapter, capability
token/object, runtime storage, physical pointer ABI, host-function pointer,
production allocation/value/cleanup executor, compiled execution, Wasm lowering,
or a `sol build` artifact. In particular, the safe ABI never exposes raw IR,
callables/functions, arbitrary pointers, mutable represented values, capability
roots/tokens, or private sources to a host callback. P3.5 owns handler frames;
P3.6 owns the complete runtime-lowered program; P4 owns Wasm emission and the
production adapter.

## Capability and Host-ABI Representation

`SolMirRuntimeHostAbi` owns bounded, same-ID/canonical-order arenas for:

1. **capability plans** — one plan for each reachable P2 capability recipe,
   retaining its recipe identity and exact representation lineage;
2. **capability sources** — a plan is classified as `ROOT`, `DERIVED`, or
   `PRIVATE_SOURCE`. `ROOT` has an entry-root coordinate; `DERIVED` retains the
   exact inherited/base source selected by the P2 construction plan; and
   `PRIVATE_SOURCE` retains the exact private source required by the P2
   representation/operation plan. No source is replaced with an ambient or
   forgeable identity;
3. **entry roots** — one descriptor for every P3.1 entry capability parameter,
   in entry formal order, with its capability recipe, P2/P3.1 provenance and
   distinct root identity. Two same-typed parameters remain distinct roots;
4. **host operations** — one descriptor per exact approved P3.1 host
   requirement, preserving receiver recipe/access, ordered argument descriptors,
   result recipe/class, closed effects, P3.1 host identity/symbol, and failure
   relation;
5. **argument descriptors** — one receiver-excluding descriptor per formal
   argument, in formal order, for the E3 data-only closure; and
6. **entry requirements and grants** — the closed required operation relation
   for each entry root and a root-specific grant relation. A grant names exactly
   `(entry, root, host operation)`; it is not capability-type-wide and cannot be
   reused for another root, derived value, or entry.

The owner borrows all predecessor records. Its own IDs are local, unstable, and
never part of canonical output. Construction is transactional into an empty
owner, with deterministic source/requirement ordering and exact limits for every
arena, owned bytes, build scratch/work, validation scratch/work, root count,
argument descriptors, requirements, and grants.

### Capability invariants

The P2 capability recipe (`SOL_MIR_RECIPE_CAPABILITY`) and its
`capability_source` relationship are authoritative. P3.4 must reconstruct the
P2 operation construction rules `ROOT_SOURCE`, `BASE_SOURCE`, and
`PRIVATE_SOURCE` exactly. A derived capability therefore remains tied to the
particular source/root from which it was constructed, while a private source
remains private metadata and is never passed across the safe host boundary.
There is no ambient capability lookup, token serialization, root equality by
type, derived-root substitution, or host-selected source.

### Historical correction: private-source construction

The frozen profile's frontend and IR require the exact declared capability
source.  A derived capability is not interchangeable with its declared source.
The former P3.4 private-source positive fixture depended on a temporary
typecheck/IR widening that accepted that substitution and has been removed.
`PRIVATE_SOURCE` construction is not source-reachable in the frozen profile;
P3.4 must not widen the language to manufacture it.  Static lineage remains
validated from authenticated predecessor records: `BASE_SOURCE` edges preserve
their exact root/parent relation and forged `PRIVATE_SOURCE` substitutions are
rejected.

Only entry capability parameters create host-bindable roots. Each is bound once
to a fresh opaque root for that entry invocation. A host operation is callable
only if its P3.1 requirement receiver is that exact bound root and its required
effect matches that root; capabilities merely reachable through derivation do
not receive an independent host grant.

## Frozen E3 Host Surface

The frozen boundary admits zero through four approved E3 requirement/import
identities, with at most one instance of each row below. P3.4 preserves their
existing P3.1 `SOL_MIR_RUNTIME_IMPORT_HOST` identities and `sol.h1` symbols;
it does not derive substitute names or assign physical imports. An unapproved
fifth import, including a same-spelled/same-effect/same-shape lookalike, is
outside the boundary rather than an alternate spelling of an approved operation.

| Capability / operation | Exact effect on `Self` | Ordered owned arguments | Result |
| --- | --- | --- | --- |
| `Console.write` | `console.write<Self>` | `Text value` | `Unit` |
| `Arguments.count` | `process.arguments.count<Self>` | none | `Int64` |
| `Arguments.get` | `process.arguments.get<Self>` | `Int64 index` | `Option<Text>` |
| `Configuration.read` | `configuration.read<Self>` | `Text key` | `Option<Text>` |

Every operation is a unique, bodyless, nongeneric capability member with exactly
one `Self`-authority effect, no result authority, no exclusive argument, and an
E3-safe result. The existing P3.1 host signature remains receiver-first:
receiver recipe/access first, followed by these formal parameters, then the
P3.1 `VALUE`/`UNIT`/`NEVER` result convention, normal/failure edges, and
normal-only exclusive writeback rule. The receiver is represented by its host
ABI root descriptor, never an argument value exposed to the callback.

### Data-only descriptors and result closure

Argument descriptors admit only `Int64`, `Bool`, `Text`, `Unit`, `Option`, and
`Result` recursively, matching the existing E3 safe-value vocabulary. A
separate test-only bounded recursive checker may inspect an authenticated
arbitrary P2 recipe and borrowed view; it has no persistent operation, grant,
callback, transfer, or production boundary meaning. Their
concrete recipe, kind, ordered child descriptors, and access are retained. The
current four imports use only owned `Text` or `Int64` arguments, but the owner
must validate the complete bounded closure rather than special-case this census.
`Text` is length-delimited bytes; sum descriptors expose only the selected
semantic case/payload, never tags, inactive storage, padding, layouts, or raw
representation bytes.

Results are not reclassified by P3.4. Every host operation references the
P3.2f same-ID host-result plan and requirement closure for its exact P3.1 host
requirement. Thus an `Int64`, `Bool`, `Text`, `Unit`, `Option`, or `Result`
result is permitted only where its P3.2f plan is eligible; `UNREACHABLE` and
`FORBIDDEN` remain distinct rejection classes. Products, arbitrary enums,
wrappers, functions, capabilities, and other out-of-closure types are rejected
transactionally.

## Entry Requirements, Grants, and Pure Preflight

For every P3.1 entry, derive the complete required host-operation relation from
the P2/P3.1 graph and associate each requirement with exactly one entry-root
identity. A valid grant set must:

- bind every required entry root exactly once and no non-entry root;
- grant every required operation exactly once on its exact root;
- contain no duplicate, omitted, unknown, bodyful, unsupported, or wrong-root
  operation;
- match receiver recipe/access, ordered descriptor recipes/accesses, result
  plan, closed effect, P3.1 host import/identity/symbol, and failure mask; and
- not grant a requirement merely because another root has the same capability
  type, name, operation spelling, or effect name.

`sol_mir_runtime_host_abi_preflight` (name subject only to normal repository API
style) is a pure, allocation-free, non-mutating checker after owner
authentication. Given one entry and a proposed bounded root/grant configuration,
it completes all structural, authority, import, descriptor, and result-plan
checks before any modeled callback or transfer. It returns a classified boundary
outcome and leaves caller state unchanged. It never invokes a host operation,
allocates, charges runtime quota, creates a capability object/token, or runs
cleanup. This is the runtime-ABI counterpart of E3's required preflight, not a
new interpreter entrypoint.

## Test-Only Host Invocation and Transfer Model

Expose a test-only finite model under the existing test-hook convention, separate
from any production adapter. It accepts an authenticated ABI owner, a preflighted
entry/root/operation grant, bounded data-only argument views, callback test
fixture, P3.2 allocation quota/usage, and bounded failure storage. It reports
only modeled success, invalid/preflight rejection, transfer limit,
allocation-limit, modeled allocation failure, host-call-limit, or host error.

The model specifies these phases, in order:

1. complete pure entry/grant/import/argument-shape preflight;
2. borrow checked argument views for the callback duration only;
3. invoke the exact root-specific test callback once, subject to the supplied
   bounded host-call limit;
4. on callback success, use the referenced P3.2f plan to perform complete
   borrowed-view-to-fresh-owned result preflight, quota checking, private
   staging, postorder rollback, nonrefunded successful charges, and single
   publication; and
5. on callback failure, produce only P3.1 `HOST_ERROR` with bounded host bytes
   (at most `SOL_MIR_RUNTIME_HOST_DETAIL_MAX`, currently 191, non-NUL bytes),
   then select the existing P3.3 cleanup/failure policy descriptively.

Neither callback inputs nor results are adopted, freed, mutated, or retained as
host storage. A successful result is fresh owned storage; a failed transfer
publishes nothing. The model does not execute runtime values, cleanup, drops,
entry bodies, interpreter code, or adapter code. It must preserve P3.3
first-failure precedence: a producing host failure is primary, and no normal
writeback or success-only action occurs on that path. It introduces no failure
code, site, mask, or execution semantics beyond references to P3.1/P3.3.

## Independent Validation, Metering, and Rendering

The validator is in a separate translation unit and reconstructs capability
plans/sources, entry roots, host operations/imports, argument descriptors,
E3 result closure, entry requirements, and grants without calling construction
helpers. Before typed traversal it validates complete predecessor chains,
capacities, raw ranges, exact arena consumption, and disjointness from every
owned arena and transitive borrowed predecessor. It rejects raw, cross-arena,
and predecessor aliases; forged same-ID records; root/source substitution;
descriptor/result-plan mismatch; import/symbol/identity collision; and all
partial or noncanonical grant coverage.

Build and validation charge checked owned bytes, scratch, and work exactly.
Persistent-owner and validator-scratch allocation-fault injection remain
deterministic. Rendering validates first, derives stable references from P3.1
host identities and P2 recipe/linkage identities, sorts canonical complete lines,
buffers all output, and performs one caller-visible write. It declares
`host-abi=true` and `host-execution=false`; it never emits dense IDs, addresses,
capacities, paths, callback contexts, roots/tokens, private sources, argument or
result bytes, allocator state, or live values. A malformed owner writes zero
bytes.

## Fixtures and Known Baseline Facts

Use the E6 all-roots fixture plus focused fixtures for:

- the closed four standard operations and their exact signatures/imports, with
  a fifth lookalike import rejected rather than admitted as a duplicate;
- two same-typed `Console` entry roots, wrong-root grants, duplicate/missing
  bindings and grants, lookalike capability/member/effect/signature rejection;
- root, derived, and private-source capability construction/provenance, including
  attempts to expose or substitute private source;
- the test-only arbitrary-recipe checker over recursive `Option`/`Result`,
  including forbidden and unreachable recipes, empty/nonempty text, malformed
  selected payloads, and borrowed argument/result aliasing without adoption;
- complete preflight before callback/allocation, host-call limits, callback
  failure detail length/NUL bounds, transfer quota/target/object/depth/node/work
  limits, refusal at each staged allocation, rollback, one publication, and
  nonrefunded quota;
- exact limits, transactional build failure, malformed mutations, raw/cross-
  arena/predecessor aliases, persistent/scratch faults, deterministic rebuild and
  render, and malformed-owner zero-write rendering.

Known E6 predecessor facts at capture: P2 linkage has four approved host
requirements; P3.1 has four host imports within 52 imports total, 18 signatures,
19 signature slots, 18 calls, 24 operands, one writeback, one entry, and 29
failure sites; P3.2f has 21 host-result plans covering those four requirements
(`UNREACHABLE` 1, `FORBIDDEN` 14, and one each of `Int64`, `Bool`, `Text`, and
`Unit`, plus `Option` 2 and `Result` 0); and P3.3 has policy only, not an
executor. Freeze new P3.4 counts and resource census from implementation rather
than guessing them here.

Post-handoff final frozen-E6 P3.4 owner census (superseding the provisional
handoff metering): 3 capability plans, 3 entry roots, 4 host operations, 3
arguments/formals/shapes, 0 shape cases, 5 requirements, and 4 grants; 1816
owned bytes, 185 build-scratch bytes, 27868 build work, 77 validation-scratch
bytes, and 8347 validation work. These are exact-limit test boundaries, not
default-limit claims. Final Debug and ASan/UBSan validation each passed 52/52.
