# P3.5 Implementation Handoff (Historical Design Snapshot)

This is the approved pre-implementation P3.5 design, captured against baseline
commit `c6c6041` (`lower bodyful capability members`), superseding the
original `0f60a61` capture for P3.5 implementation. That prerequisite narrowly
supports bodyful root-capability members internally with receiver-first
signatures/contracts; derived/private-source bodyful members remain unsupported,
and bodyless members remain imports. Focused handler providers must be bodyful
pure root-capability members so their binding is an internal P3.1 target. It is not a
progress report or a second queue: `TODO.md` remains the live and sole
authority for work status and execution order. At capture, P3.1--P3.4 were
complete for the frozen E6 profile and P3.5 was the next production checkpoint.

## Objective and Boundary

Add a separate, bounded, backend-independent `SolMirRuntimeHandlerAbi` owner.
It borrows authenticated immutable P3.1 runtime conventions, P3.2 runtime
values, P3.3 cleanup policy, and P3.4 host ABI; all predecessors must outlive
it. The owner freezes the static handler-frame ABI and supplies a finite,
test-only activation-stack model for the existing exact-handler semantics.

P3.5 reuses, rather than duplicates or reinterprets, P2 concrete handler
markers/bindings, places, values, operations, signatures, effects, and source
provenance; P3.1 imports/call signatures/failure sites; P3.2 value plans; P3.3
cleanup transitions; and P3.4 capability-root lineage. It must not renumber or
broaden any predecessor record.

P3.5 does not add resumptive/general handlers, a runtime executor, storage,
allocation, capability tokens, a host adapter, physical ABI, backend lowering,
Wasm emission, compiled execution, or `sol build`. P3.6 owns integration and
validation of the complete runtime-lowered program; P4 owns backend execution.

## Frame Plans

`SolMirRuntimeHandlerAbi` owns one canonical same-ID **frame plan** for every
reachable P2 concrete handler binding. Same-ID means the frame plan retains the
authenticated concrete handler identity; its local arena index is unstable and
must not appear in canonical output.

Each frame plan contains exactly:

- the handler's source operation identity and authenticated source provenance;
- the exact authority root and normalized closed effect required to intercept
  that operation;
- the provider's canonical place and provider value plan, including its access
  and ownership relation;
- the exact internal provider operation and its P3.1 internal call signature;
- the P2 enter/exit handler marker provenance delimiting the lexical lifetime;
  and
- its runtime activation parent relation.

The provider is not resolved by spelling, capability type, compatible effect,
or source-location coincidence. Its place/value/internal-operation/signature
records must be the exact authenticated P2/P3.1 records selected by the
concrete binding. A frame cannot substitute a derived root for a declared root,
or one provider/signature for an otherwise similar one.

The static parent relation is the lexical enclosing handler frame, or `NONE`.
At runtime, activation creates a corresponding parent-linked frame only while
the handler scope is live. Static frame plans therefore describe possible
frames; they are not ambient authority and are not an always-active handler
table.

## Exact Dispatch and Activation Semantics

An operation is intercepted only by an active frame whose source operation,
authority root, and closed effect are all exact matches. Matching is identity
based after predecessor authentication; subset effects, same-named operations,
same-typed roots, source lookalikes, and provider signature compatibility do
not match.

To invoke a matched provider:

1. locate the innermost matching active frame;
2. hide that frame and every younger frame from handler dispatch;
3. invoke the frame's exact internal provider operation using its retained
   place/value and P3.1 signature; and
4. restore the hidden suffix, in its original order, on either provider success
   or provider failure before continuing the selected normal/failure path.

Hiding prevents a provider from recursively observing its own intercepted
operation and preserves nested LIFO behavior. Older frames remain visible while
the suffix is hidden. A provider can therefore be handled only by an older exact
match, if one exists. Nested older-provider invocation under an already hidden
suffix restores the suffix in LIFO order. The model must restore the identical activation state on
both success and failure; restoration is not a cleanup action and must occur
before P3.3's selected transition is observed.

A normal handler entry evaluates the provider expression/value first. Only
after that evaluation succeeds does the model push the new runtime activation
frame. Thus a provider-evaluation failure leaves no newly active frame. The
frame is popped exactly once when its lexical scope leaves: either at the exact
P2 `EXIT_HANDLER` marker or through the corresponding P3.3 `EXIT_HANDLER`
cleanup action on normal, transfer, and failure paths. The two records describe
the same pop, not two pops. Missing, duplicated, crossed, non-LIFO, or
unbalanced entries/exits are invalid.

## Test-Only Stack API

Expose a bounded test-hook API, separate from production execution, that accepts
an authenticated handler ABI owner and a caller-owned bounded activation stack.
It may model provider evaluation, push, exact dispatch, hidden-suffix provider
invocation, restoration, and marker/cleanup-directed pop. It reports classified
model outcomes only and never executes P2 CFGs, runtime values, cleanup, host
callbacks, allocation, or compiled code.

The stack model must make these observable to tests:

- current active frame order and parent relation;
- exact-match versus no-match selection;
- the hidden suffix while a provider is invoked;
- restoration after modeled success and failure; and
- one pop attributed to the matching P2 marker or P3.3 action.

It must reject unauthenticated plans, stale/wrong parent activation, wrong
root/effect/operation/signature, push-before-provider-success, stack overflow,
underflow, crossed exits, double pop, and restoration of a non-hidden or altered
suffix. It creates no new runtime failure code, site, import, cleanup policy, or
authority grant.

## Independent Validation, Metering, and Rendering

Construction is transactional into an empty owner and is bounded by exact frame
count, marker references, owned bytes, build scratch/work, validation
scratch/work, and test-stack limits. Canonical construction order follows the
authenticated P2 concrete-handler order.

A separate validator must reconstruct the complete frame-plan relation without
calling construction helpers. Before typed traversal it validates predecessor
chains, capacities, raw ranges, complete arena consumption, same-ID coverage,
and disjointness from every owned arena and every transitive borrowed
predecessor. It must independently check exact source/root/effect matching,
provider place/value/internal-operation/signature provenance, lexical parents,
P2 enter/exit pairing, and P3.3 `EXIT_HANDLER` correspondence.

Reject raw, forged, cross-arena, or predecessor aliases; partial same-ID
coverage; substituted roots/effects/providers/signatures; marker/action
mismatch; invalid parent relations; and any non-LIFO or multiply represented
pop. Build and validation meter checked owned bytes, scratch, and work exactly;
persistent-owner and validator-scratch fault injection remain deterministic.

Rendering validates first, buffers all output, and performs one caller-visible
write. It derives stable references only from predecessor canonical identities,
renders complete canonical frame and parent relations, and declares
`handler-abi=true` and `handler-execution=false`. It must not render dense IDs,
addresses, capacities, paths, live stack contents, provider bytes, runtime
values, roots/tokens, or private sources. A malformed owner writes zero bytes.

## Fixtures and Baseline Census

The E6 all-roots fixture has **zero handler frame plans** at this baseline. That
zero is an acceptance boundary: P3.5 must successfully construct, validate, and
render an empty handler ABI without inventing records or changing any inherited
E6 census.

Add focused handler fixtures and slices outside the E6 closure for:

- one exact handler and provider with enter/exit provenance;
- nested handlers with distinct and identical-looking operation/root/effect
  combinations, proving innermost exact selection and older-frame visibility;
- source, root, effect, provider place/value/internal operation, and signature
  lookalikes that must not intercept;
- provider evaluation failure before push;
- matched-frame plus younger-frame hiding, then exact restoration on provider
  success and provider failure;
- normal exit, return/transfer, and failure cleanup, proving the exact P2 marker
  or P3.3 `EXIT_HANDLER` action pops once and only once;
- malformed parent chains, marker pairing, cleanup correspondence, aliases,
  limits, transactional failure, allocation faults, deterministic rebuild, and
  zero-write malformed rendering.

Historical design note: this capture deliberately left the focused nested-handler
census provisional. The completed implementation froze it at 7 frames, 14 exit
markers, 8 cleanup exits, 29 marker references, maximum stack depth 7, test work
7, 2152 owned bytes, build scratch 56, build work 7809, validation scratch 56,
and validation work 12251. Empty E6 has zero counts, storage, and scratch, with
build work 22 and validation work 2707. Final Debug and ASan/UBSan each passed
53/53.

## Resumption Slices

1. Add the public/internal `mir_runtime_handler_abi` API, limits/usage,
   transactional owner, same-ID frame plans, exact predecessor references, and
   canonical parent relation.
2. Add independent validation, complete metering, anti-alias/fault hardening,
   and empty-E6 plus focused handler fixture construction.
3. Add the bounded test-only activation stack: evaluate-before-push, exact
   selection, hidden-suffix provider invocation, success/failure restoration,
   and exact marker/cleanup pop.
4. Add canonical rendering, deterministic and malformed zero-write tests, and
   freeze the focused nested-handler census.

These are interruption boundaries within P3.5, not completed roadmap items. Do
not update `TODO.md` or status documents while implementing them.
