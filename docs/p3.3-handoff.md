# P3.3 Implementation Handoff (Historical Design Snapshot)

This is the approved pre-implementation P3.3 design captured against baseline
commit `56edb8f` (`close runtime value operation plans`), with the required
executable lexical-scope-marker correction from `e08bb93` (`retain executable
lexical scope markers`). It is deliberately not
a progress report or a second work queue. `TODO.md` is the live and sole
authority for status and execution order.

## Objective and Boundary

Add a separate bounded `SolMirRuntimeCleanup` owner. It borrows the already
authenticated, immutable `SolMirRuntimeConventions` and
`SolMirRuntimeValues` owners; both must outlive it. It freezes a
backend-independent cleanup, panic-detail, and failure-transition policy for
the complete P2 graph. It reuses P3.1 call/result/failure conventions and P3.2
ownership/drop plans; it neither duplicates nor changes their records,
symbols, recipe digests, layouts, imports, failure codes, or source sites.

P3.3 describes policy only. It does **not** add a runtime executor, storage,
allocator, physical ABI/pointer representation, host adapter/authority API,
handler ABI, MIR/P2 rewrite, interpreter behavior change, Wasm lowering, or
compiled execution. P3.4 owns capability and trusted-host ABI, P3.5 handler
frames, and P3.6 integrates the complete runtime-lowered program.

## Owned Representation

`SolMirRuntimeCleanup` owns four bounded arenas:

- **events**: one same-ID event record for each P2 terminal or fallible
  operation occurrence, with its source callable/block/operation provenance,
  explicit versus implicit origin, and primary normal/failure meaning;
- **actions**: a contiguous, ordered action slice for each event;
- **transitions**: event outcomes to normal continuation, return/exit, or
  selected failure propagation, including the cleanup slice and precedence
  relation; and
- **supplemental sites**: canonical source-aware sites for failure producers
  P3.1 intentionally did not own.

All construction is transactional and bounded by exact arena counts, owned
bytes, build scratch, and work. Same-ID and source ordering follow the P2/P3.1
owners. The cleanup owner must authenticate both predecessors before consuming
their graph and must reject any raw-range, cross-arena, or predecessor alias
before dereferencing it.

### Events and failure sites

An **explicit** event is a graph-directed return, propagation, scope/region
exit, break/continue, or explicit `panic`/`unreachable` transition. Its
existing P3.1 failure site is reused when it has one. An **implicit** event is
introduced by a fallible runtime operation or check: host failure,
arithmetic failure, allocation-limit/allocation failure, no-match,
contract/refinement violation, or reached-unreachable. Each such producer has
one supplemental site whose source provenance and failure-code mask are
canonical and stable. Supplemental sites supplement P3.1; they never renumber,
replace, or broaden a P3.1 site.

Panic detail is captured at the producing event before cleanup begins: the
stable failure identity/code, source-aware site, and the bounded kind-specific
detail needed for diagnostics (for example checked arithmetic, allocation,
no-match, contract/refinement, or reached-unreachable detail). Cleanup does not
overwrite, borrow transient storage for, or otherwise lose that detail.

## Exact Action Vocabulary and Ordering

Actions are static descriptions, not calls to a destructor. They refer to the
P3.2c ownership/drop plan for the target and never visit a moved root, hole,
inactive sum payload, padding, borrowed token, or uninitialized value.

The action kinds are:

1. `WRITEBACK` — normal-edge exclusive receiver/argument writeback only, in
   receiver-first formal order already frozen by P3.1;
2. `CHECK_CONTRACT` — evaluate the applicable requires/ensures/refinement
   phase and select its normal or failure transition;
3. `DROP_TEMPORARY` — destroy a live temporary in reverse creation order;
4. `DROP_PLACE` — destroy a live local root or still-live projected remainder
   using its P3.2 ownership plan; roots in a lexical scope are reverse
   declaration/initialization order;
5. `EXIT_SCOPE` — close a lexical scope only after all of its temporary and
   root actions complete;
6. `EXIT_REGION` — leave an explicit region after its contained scopes; nested
   regions leave inner to outer;
7. `DROP_SNAPSHOT` — release a captured contract snapshot in reverse capture
   order, after every contract check that can read it;
8. `DROP_PARAMETER` — release owned callee parameters in reverse formal order;
   shared/exclusive borrow tokens are not dropped; and
9. `PROPAGATE_FAILURE` — transfer the already selected primary failure to the
   P3.1 failure edge, caller, or entry exit after cleanup.

For every transition, actions execute in their listed phase order. Thus normal
call writeback occurs only on its normal edge and before the continued program
can observe it. Contract checks occur before snapshot release; on a successful
terminal path, all live temporaries, scope roots, regions, snapshots, and owned
parameters are then cleaned in the listed order. A scope/region transfer cleans
only the exited suffix, innermost first. Return cleans all remaining callable
scopes before snapshots and parameters. Propagation and panic suppress normal
writeback; they run applicable failure-contract checks only where the frozen P2
contract outcome says failure is checked, then use the same reverse-lifetime
cleanup order and propagate last. No cleanup action itself is fallible.

## Failure Precedence

The event's producing failure is captured first and is the primary failure.
Cleanup cannot replace it. A normal-only writeback or success-only
postcondition is never attempted on a failure path. If an applicable
failure-contract/refinement check fails while a failure is already pending,
the original primary failure wins; the later violation is retained only as
bounded secondary detail if the policy records it. If a normal-path contract
or refinement check fails, it becomes the primary failure before the ensuing
cleanup. This supplies deterministic first-failure precedence for nested
regions, propagation, and all implicit producers without inventing a new P3.1
failure identity.

## P3.1 and P3.2 Allocation/Resource Relationship

P3.1 sites remain authoritative for call/result/failure-convention producers.
P3.3 supplemental sites are only the implicit cleanup-policy producers listed
above. P3.2 allocation plans and their existing allocation-limit/failure
mapping remain authoritative for resource requests; P3.3 selects the
transition, panic detail, cleanup, and precedence after such a result. It does
not create allocation plans, resource imports, or physical allocations.

## Validation, Metering, and Rendering

The independent validator must reconstruct events, action slices, transitions,
explicit/implicit site selection, liveness/ownership eligibility, exact action
ordering, writeback and contract gating, panic-detail capture, and
first-failure precedence without calling construction helpers. It consumes all
arenas exactly and validates complete predecessor ranges and anti-aliasing
before access. Build and validation meter checked bytes, work, and scratch
exactly; persistent-arena and validator-scratch fault selection remains
deterministic.

Canonical buffered rendering declares `cleanup-policy=true` and
`cleanup-execution=false`. It emits stable digest-keyed event/action/transition
descriptions and supplemental-site provenance, never raw IDs, addresses,
capacities, paths, allocator state, live values, or panic payload contents. A
malformed owner produces zero output bytes.

## Test Policy

Provide a test-only finite cleanup-policy trace API, separate from production
execution. It accepts an authenticated cleanup owner and bounded abstract
liveness/outcome inputs, and reports the selected transition, ordered action
trace, primary failure, and bounded captured detail. It must not allocate or
execute runtime values, host calls, ABI marshalling, or real drops.

Cover every action kind and event class; normal return; explicit propagation,
panic, unreachable, break/continue, scope and nested-region exit; host,
arithmetic, allocation-limit/allocation-failure, no-match, contract and
refinement failures; moved/partly moved roots; temporary and snapshot ordering;
owned versus shared/exclusive parameters; normal-only writeback; success and
failure contract gates; panic-detail survival; and primary-versus-secondary
first-failure precedence. Also cover exact limits, malformed mutations,
raw/cross-arena/predecessor aliases, persistent and scratch allocation faults,
determinism, and malformed-owner zero-write rendering.
